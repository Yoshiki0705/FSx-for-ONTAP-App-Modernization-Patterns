# 陽性対照のない計測は結論にならない

>
> 証拠区分: 本文の事実は段階 0〜3 の run に基づく `verified` と、AWS の価格情報に基づく `documented`。
> この Spoke の 1 つのサンプルアプリで得た経験で、他の環境や他のプロジェクトへの一般化は書かない。

段階 0〜3 の計測と文書化で、結果の読み方を変えた事例が 4 つあった。
各節は、事実（run id と日付）、続けて読者が取る手順の順に書く。

## 陽性対照を欠いた計測の無効

段階 0〜2 の `case-sensitivity` の記録（run id `s0`、`s1`、`s2`、`s2f`、`s2g` 系、2026-10-07〜11）は、
結論に使えない。Probe は参照 `Docs\Index.json` をボリュームのルートに対して引いたが、実ファイルは
`seed/docs/index.json` にあった。実ファイルを正しいケースで引く陽性対照（`real`）が、全件で記録されていなかった。
このため、大文字小文字を区別しない Windows SMB でも `resolved: false` と記録され、その値が
「区別する」の観測なのか、「ファイルがそこに無い」だけなのかを、記録から判別できなかった。
`compare-probe.py` は、段階 1（2026-10-07）で、陽性対照のないこの記録同士を比べて `ok` と判定していた。
2026-10-12 に次の変更を入れた。

- 参照を `seed/` 配下に固定した
- `real` と `real_resolved` を記録に加えた
- 陽性対照が解決したときだけ `outcome` を `measured` にする

再計測は、SMB と NFS が `s4c-20261012T034403Z`（Windows SMB、Linux cifs、Linux NFS）、
S3 Access Points が `s3b-20261012T022900Z` で、ONTAP 9.19.1P3、Single-AZ、ntfs ボリューム 1 つ、各 1 回である。
結果は[段階 1](stage-1-multiprotocol.md)と[段階 3](stage-3-s3-access-points.md)にある。

## ゲートの成功と実行の区別

検査の「0 件」は、「問題が無い」と「検出できていない」の両方に読める。
この Spoke では、次の 3 点で「走った」ことを確かめる。

- Makefile の全ターゲットを `.PHONY` で宣言する。ディレクトリと同名のターゲット（`docs`、`templates`、`scripts`）は
  宣言がないと「up to date」と表示されて何も実行されない
- 検査ツールが無いときはスキップせず失敗させる。スキップを成功と報告すると、通った検査と区別できない
- 各検出器は、走査の前に自分の selftest を実行する。規則が一致しなくなった検出器は、空の結果を合格として返さず失敗する

詳細は[品質ゲート](../agent/quality-gates.md)にある。
AIMF のセッションでも、移行の観点の検出器（AP-1〜13）に一時的な違反ファイルを注入し、全件が検出されること
（pass 13、fail 0、2026-10-12）を確かめてから、検出器の「0 件」を信用した。
パイプ越しの終了コード（`make all | tail`）は `tail` のものになるので、ゲートの合否は
`make all > /tmp/all.log 2>&1; echo $?` で読む。

## 静的ページの取得が見落とす動的タブ

S3 Access Points のリクエスト料金は、Amazon FSx for NetApp ONTAP の英語版の料金ページで、
スクリプトにより描画されるタブ（「S3 Access Points for FSx」）にある。<!-- allow:naming -->
静的な HTML の取得では、このタブの内容が出ない。日本語版の料金ページには、2026-10-12 時点でこのタブが無かった。
日本語ページだけを見て「S3 Access Points の要求は課金されない」と読むと、誤りになる。
同じ単価は、AWS Price List API のサービスコード `AmazonS3`（`APN1-Requests-FSXONTAP-Tier1` と `Tier2`、
Asia Pacific (Tokyo)）で、2026-10-12 に確認した。経緯と単価は[段階 3](stage-3-s3-access-points.md)の見積りの節にある。

## 自己申告ラベルと観測の区別

Probe の標準出力と、S3 の Lambda 単独呼び出しの JSON は、2 台が協調していなくても `"topology": "cross-host"` を出力する。
このラベルは固定値で、観測を表さない。2 台の協調と認めるのは、`probe_merge.py` が、同期 ID の一致と時刻の重なりを
両側の記録から確認し、`reasons` が空で `cross-host` と判定した組だけである。
同じ理由で、2026-10-07 の段階 0 の記録にあった `cross-host` の主張は撤回した
（[段階 0](stage-0-smb-ntfs.md)の撤回の節）。Probe の出力形式は[サンプルアプリ](sample-app.md)にある。

## 利用者が取る手順

- 計測には陽性対照を組み込む。対象が「無い」ことと、「在るのに解決しない」ことを、同じ記録の中で区別できるようにする
- 比較ツールの判定は、両側の記録が有効なときだけ使う。無効な記録同士の `ok` は、一致の証拠にならない
- 検出器とゲートは、通してはいけない入力で落ちることを確かめてから信用する
- 動的に描画されるページは、別言語のページ、価格 API など、複数の経路で確かめる
- ラベルや分類は、それを導いた証拠と同じ場所で判定する。証拠がないときはラベルを付けない
